Задание F. Анализ HTTP-сообщений

F1. Разбор запроса и ответа

1. Метод "POST", путь "/api/login", версия "HTTP/1.1". Клиент отправляет данные для входа в систему.

2. "Content-Type: application/json" — тело запроса в формате JSON; "Accept: application/json" — клиент ожидает JSON в ответе; "Content-Length: 48" — размер тела запроса в байтах.

3. "200 OK" означает успешное выполнение запроса. В теле ответа содержатся идентификатор пользователя "42" и его роль "STUDENT".

4. Атрибуты cookie:
   
   - "HttpOnly" — запрещает доступ к cookie из JavaScript.
   - "Secure" — cookie передаётся только через HTTPS.
   - "SameSite=Lax" — ограничивает отправку cookie в межсайтовых запросах.
   - "Max-Age=3600" — cookie действует 3600 секунд, то есть 1 час.

5. Следующий запрос:
   
   GET /api/students/42 HTTP/1.1
Host: uni.example
Cookie: session=abc123
Accept: application/json
   
   Заголовок "Cookie" передаёт идентификатор сессии, по которому сервер может определить пользователя.

6. "Cache-Control: no-store" запрещает сохранять ответ в кэше. Это снижает риск сохранения конфиденциальных данных пользователя.

7. Пароль нельзя передавать по обычному HTTP, поскольку данные могут быть перехвачены при передаче. HTTPS шифрует соединение и защищает пароль от прочтения посторонними.

F2. Подбор статус-кодов

№| Код| Обоснование
1| "200 OK"| Профиль успешно получен.
2| "201 Created"| Создан новый студент.
3| "204 No Content"| Студент удалён, тело ответа отсутствует.
4| "301 Moved Permanently"| Адрес перенесён навсегда.
5| "400 Bad Request"| Некорректный синтаксис JSON.
6| "401 Unauthorized"| Пользователь не прошёл аутентификацию.
7| "403 Forbidden"| Пользователь вошёл, но не имеет нужных прав.
8| "404 Not Found"| Студент не найден.
9| "409 Conflict"| Email уже используется.
10| "422 Unprocessable Content"| Значение оценки не проходит проверку.
11| "429 Too Many Requests"| Превышен лимит запросов.
12| "500 Internal Server Error"| Необработанное исключение на сервере.
13| "502 Bad Gateway"| Reverse proxy не получил корректный ответ от backend.
14| "304 Not Modified"| Ресурс не изменился; можно использовать кэшированную версию.

F3. Написание HTTP-запросов

1. Получить студента 42

GET /api/students/42 HTTP/1.1
Host: uni.example
Accept: application/json

2. Создать студента

POST /api/students HTTP/1.1
Host: uni.example
Content-Type: application/json
Accept: application/json

{"firstName":"Anna","lastName":"Ivanova","group":"IS-21"}

3. Полностью заменить данные студента 42

PUT /api/students/42 HTTP/1.1
Host: uni.example
Content-Type: application/json
Accept: application/json

{"id":42,"firstName":"Anna","lastName":"Ivanova","group":"IS-21"}

4. Изменить только группу

PATCH /api/students/42 HTTP/1.1
Host: uni.example
Content-Type: application/json
Accept: application/json

{"group":"IS-22"}

5. Удалить студента 42

DELETE /api/students/42 HTTP/1.1
Host: uni.example
Accept: application/json

6. Получить вторую страницу группы IS-21 по 20 записей

GET /api/students?group=IS-21&page=2&limit=20 HTTP/1.1
Host: uni.example
Accept: application/json

F4. Диагностика

№| Вероятная стадия и первая проверка
1| DNS. Проверить правильность доменного имени и результат "nslookup".
2| Сеть / сервер. Проверить, запущено ли приложение на порту 3000 и правильный ли указан порт.
3| Аутентификация. Проверить, почему запрос не содержит заголовок "Authorization", и добавить токен, если он требуется API.
4| Маршрутизация API. Исправить путь на "/api/students/42" согласно документации.
5| Frontend. Проверить структуру JSON и заменить "response.items" на "response.data", если это соответствует формату ответа.
6| Backend. Изучить stack trace и проверить, почему происходит обращение к "undefined".
7| Браузер / CORS. Проверить сообщение консоли, адреса источника и сервера, а также настройки CORS на сервере.

F5. Повторная отправка POST-запроса

1. После обрыва соединения клиент не знает, успел ли сервер создать заказ.
2. Если повторить запрос, сервер может создать второй заказ и списать оплату повторно.
3. Если не повторять запрос, заказ может остаться несозданным, даже если пользователь считает, что он оформлен.
4. Решение — использовать уникальный ключ идемпотентности ("Idempotency-Key"), который клиент передаёт вместе с запросом. Сервер сохраняет результат операции и при повторном запросе с тем же ключом возвращает прежний результат, не создавая второй заказ. Также можно проверить состояние заказа отдельным запросом. Идемпотентность означает, что повтор операции не приводит к дополнительному изменению состояния.
